## 1. 一句话概述

在沸点火锅点单演示产品中新增智能推荐菜能力，使点餐用户在菜单页获得基于口味偏好、菜品热度、时段和搭配维度的个性化菜品推荐，从而提升点餐效率和订单转化率，同时保持现有分类浏览、搜索、规格选择、购物车、下单等全流程不受影响。

---

## 2. 背景与目标

### 背景
- 当前菜单页的"推荐"分类（`menu.cat.recommend`）实际为"显示全部菜品"的筛选入口，无任何智能推荐逻辑。
- 系统为纯前端 SPA（React + Vite），无后端服务、无用户账号体系、无跨会话订单历史持久化，所有状态由 `useReducer` 在客户端管理，页面刷新或 RESET 后状态清空。
- 菜品数据为静态演示数据（`src/data/menu.ts`，共 10 个菜品），部分菜品带有 `badge`（人气/招牌/主厨推荐/新品）和 `orderedCount`（已点台数）字段，但无结构化口味标签。
- 用户希望系统能根据历史点餐、菜品热度、口味标签、时段、搭配等多维度智能推荐，但当前架构不具备真实用户数据和推荐算法基础设施。

### 目标
- 在菜单页为用户提供可见的个性化推荐菜品展示，覆盖至少 3 种推荐维度：菜品热度排行、时段推荐、口味偏好匹配，以及搭配推荐。
- 推荐菜品可直接加入购物车，与现有点餐流程无缝衔接。
- 推荐逻辑基于客户端可获取的数据（菜品属性、当前会话行为、时段、模拟偏好画像）运行，无需后端服务。
- 推荐展示在视觉上与现有菜单分类区域区分，用户能直观识别"推荐"与"全部菜品"。
- 中英文双语支持推荐相关文案。

### 不做（本次范围外）
- **不引入后端推荐服务或算法引擎**：推荐逻辑在前端客户端完成，不新增服务端接口（`/ping` 保持不变）。
- **不引入用户账号/登录体系**：推荐基于当前会话行为和模拟偏好画像，不依赖跨设备用户画像。
- **不修改现有点餐核心流程**：分类浏览、搜索、规格选择（份量/口味/辣度）、超级辣风险提示、购物车、下单、订单履约、结账等链路保持不变。
- **不重构菜单数据为动态接口**：菜品数据仍为 `src/data/menu.ts` 静态数据，推荐逻辑在此基础上计算。
- **不做 A/B 测试或推荐效果数据分析**：本次为概念演示功能，不接入数据采集和效果度量。
- **不做 localStorage 跨会话偏好持久化**：偏好画像为模拟数据，会话行为仅当前会话有效，不跨会话存储。

## 3. 需求详情

### 用户场景

| 场景 | 用户与上下文 | 期望结果 |
|------|-------------|---------|
| S1 首次进入菜单页 | 用户绑桌后进入菜单页，面对 10 个菜品不知选什么 | 看到精选推荐菜品（基于模拟偏好+热度），快速决策 |
| S2 浏览热度排行 | 用户想知道哪些菜受欢迎 | 推荐区域包含按热度/销量排序的菜品 |
| S3 时段适配推荐 | 用户在午餐/晚餐/夜宵时段进入 | 推荐内容贴合当前就餐时段 |
| S4 口味偏好推荐 | 用户有辣度/菜系偏好 | 推荐菜品匹配用户模拟口味画像（tags 匹配） |
| S5 搭配推荐 | 用户选了主菜后犹豫配菜 | 看到主菜+配菜+饮品组合建议，可一键加购 |
| S6 已选菜品去重 | 推荐中已加入购物车的菜品 | 推荐列表标记"已加购"或移出推荐 |
| S7 会话行为影响推荐 | 用户在会话中加了多个辣味菜品 | 后续推荐提升辣味菜品权重 |

### 用户路径（主流程：浏览推荐并加购）

1. 用户完成绑桌，进入欢迎页，点击"开始点餐"进入菜单页。
2. 菜单页分类 Tab 上方展示"为你推荐"横滑卡片区域，包含 3-6 个推荐菜品，每张卡片附带推荐理由标签（如"人气 No.1""午餐热门""辣味爱好者"等）。
3. 用户横滑浏览推荐菜品，点击某推荐菜品卡片。
4. 弹出规格选择 Dialog（与现有点餐流程一致），用户选择份量/口味/辣度/用餐人后加入购物车。
5. 推荐区域自动刷新，已加入购物车的菜品标记"已加购"或移出推荐列表，推荐列表动态补充新菜品。

### 用户路径（搭配推荐）

1. 用户在菜单页选择了一个主菜（如牛肉/锅底）并加入购物车。
2. 系统识别购物车内已有主菜，推荐区域出现"搭配推荐"模块，建议搭配配菜和/或饮品，附带"一键加入搭配"按钮。
3. 用户点击"一键加入搭配"，系统将搭配组合的多道菜品同时加入购物车（使用默认规格），或用户可逐个点击搭配卡片单独加购。
4. 搭配推荐随购物车内容变化动态更新。

### 产品规则

#### 推荐展示位置与布局
- 推荐菜品在菜单页分类 Tab 上方新增独立横滑卡片区域展示，标题为"为你推荐"。
- 现有 `menu.cat.recommend` Tab 保持"显示全部菜品"行为不变，推荐区域独立于 Tab 系统。
- 推荐区域与搜索框/分类 Tab 在视觉上有间距区分，不遮挡或推开搜索框和分类 Tab。

#### 推荐维度与逻辑
- **菜品热度排行**：基于 `orderedCount` 和 `badge`（popular/signature/chef）排序，热度高的菜品优先推荐。
- **时段推荐**：根据当前系统时间划分时段，展示该时段热门菜品。时段划分：
  - 午餐：10:00 - 14:00
  - 晚餐：17:00 - 22:00
  - 夜宵：22:00 - 02:00（跨日）
  - 其他时段（02:00-10:00、14:00-17:00）：默认使用"全天热门"推荐，不标时段标签。
- **口味偏好匹配**：基于模拟用户口味画像（硬编码偏好 tags，如 `['辣','肉类','招牌']`），与菜品新增的 `tags` 字段做匹配，匹配度高的菜品优先推荐。会话内用户加购行为动态调整推荐权重：
  - 用户加购含 `tags: ['辣']` 的菜品 → 后续推荐提升辣味菜品权重。
  - 用户加购含 `tags: ['海鲜']` 的菜品 → 后续推荐提升海鲜类菜品权重。
- **搭配推荐**：购物车内已有主菜（category 为 `menu.cat.broth` 或 `menu.cat.meat`）时，推荐互补菜品（category 为 `menu.cat.veggie` 或 `menu.cat.staple`），组成"主菜+配菜+饮品"搭配，展示"一键加入搭配"按钮。

#### 推荐数量
- 推荐区域展示 3-6 个推荐菜品，避免信息过载。
- 搭配推荐模块展示 2-3 个搭配菜品组合建议。

#### 去重规则
- 已加入购物车的菜品在推荐列表中标记"已加购"并降低推荐优先级，或直接移出推荐列表。
- 售罄菜品（`soldOut` 列表中的 `productId`）不出现在推荐列表中。

#### 推荐理由标签
- 每个推荐菜品附带简短推荐理由标签，中英文双语，包括但不限于：
  - 热度类："人气 No.1" / "Top Pick"
  - 时段类："午餐热门" / "Lunch Favorite"
  - 口味类："辣味爱好者" / "Spicy Lover"
  - 搭配类："搭配牛肉" / "Pairs with Beef"
- 同一菜品可展示多个推荐理由标签，按优先级排列，最多显示 2 个。

#### 推荐刷新时机
- 用户进入菜单页时初次计算推荐。
- 购物车变化（加购/改数量/移除）时重新计算推荐。
- 时段切换时重新计算推荐（前端定时检测当前时段是否变化）。

#### 模拟偏好画像
- 演示用模拟用户口味画像，硬编码在前端配置中，例如：`{ tags: ['辣', '肉类', '招牌'], spicyPreference: 'medium' }`。
- 画像在 `RESET` 后恢复初始值。
- 不做跨会话持久化，页面刷新后恢复初始模拟画像。

#### 搭配推荐一键加购
- 搭配组合中每道菜品使用默认规格（份量=full、口味/辣度取第一个选项、用餐人取第一个 diners）。
- 点击"一键加入搭配"后，搭配组合中的所有菜品同时加入购物车。
- 用户也可逐个点击搭配卡片中的菜品单独加购（弹出规格选择 Dialog）。

### 状态与反馈

- **成功**：用户进入菜单页即可看到推荐区域，包含推荐菜品和推荐理由标签，推荐菜品可正常加购，搭配推荐可一键加购。
- **失败**：推荐逻辑异常或数据不足时，降级为隐藏推荐区域或回退为展示全部菜品（不影响分类 Tab 正常使用），不阻断点餐流程。
- **空态**：无可用推荐菜品时（如全部售罄），推荐区域展示引导文案"暂无推荐，请浏览全部菜品"。
- **无权限**：本产品无权限体系，不涉及。
- **异常**：推荐计算出错时静默降级，用户无感知，不影响正常点餐。
- **保持不变**：现有分类浏览、搜索、规格选择、超级辣风险提示、购物车、下单、订单、呼叫服务、结账全流程不受影响。现有 `menu.cat.recommend` Tab 行为（显示全部菜品）不变。

### 关键文案

- 推荐区域标题："为你推荐" / "Recommended For You"
- 推荐理由标签：
  - "人气 No.1" / "Top Pick"（热度）
  - "午餐热门" / "Lunch Favorite"（时段）
  - "晚餐热门" / "Dinner Favorite"（时段）
  - "夜宵热门" / "Late Night Favorite"（时段）
  - "辣味爱好者" / "Spicy Lover"（口味）
  - "搭配牛肉" / "Pairs with Beef"（搭配）
- 已加购标记："已加购" / "Added"
- 空态提示："暂无推荐，请浏览全部菜品" / "No recommendations, browse all dishes"
- 搭配推荐标题："搭配推荐" / "Combo Suggestions"
- 一键加购按钮："一键加入搭配" / "Add Combo"

### 关键表现要求

- 推荐区域为横滑卡片布局，卡片宽度小于分类浏览网格卡片（紧凑展示），与现有菜单卡片视觉风格一致（圆角卡片 + 图片 + 名称 + 价格 + 推荐理由标签）。
- 推荐区域在浅色/深色模式、老人模式下均正常显示，卡片间距、字号、对比度满足现有设计规范。
- 推荐区域不应遮挡或推开分类 Tab 和搜索框，不干扰用户正常浏览全部菜品。
- 推荐理由标签使用现有 badge 视觉样式（圆角胶囊 + 琥珀色底），不引入新色系。
- 横滑区域支持触摸滑动和鼠标拖拽，滚动条隐藏（`scrollbar-none`）。

## 4. 约束限制

- **架构约束**：纯前端实现，不新增后端服务或接口，推荐逻辑在客户端 JavaScript 中完成。
- **数据约束**：菜品数据为 `src/data/menu.ts` 静态数据（10 个菜品），需为 `Product` 类型新增 `tags: string[]` 字段。推荐逻辑需在此数据集上有效。
- **偏好数据约束**：模拟用户口味画像为硬编码配置，不做 localStorage 持久化，会话行为仅当前会话有效。
- **性能要求**：推荐计算在前端同步完成，不增加可感知的页面加载延迟（<100ms）。
- **兼容要求**：推荐功能须兼容浅色/深色模式、老人模式、中英文切换，不破坏现有视觉一致性。
- **稳定性要求**：推荐逻辑异常时必须自动降级为现有行为（隐藏推荐区域或显示全部菜品），不抛出未捕获错误。
- **实现边界**：不引入机器学习库或外部推荐 SDK，推荐逻辑为基于规则的客户端算法。
- **保持不变**：`orderReducer` 现有 action 类型和行为不变，可新增推荐相关 state 字段但不修改现有字段语义。`menu.cat.recommend` Tab 行为不变。

## 5. 验收标准

- [主流程] 在用户绑桌进入菜单页后，分类 Tab 上方应展示"为你推荐"横滑区域，包含 3-6 个推荐菜品，每张卡片附带推荐理由标签。
- [热度推荐] 推荐列表中应包含 `orderedCount` 最高的菜品或 `badge` 为 popular/signature/chef 的菜品，并附带热度类推荐理由标签。
- [时段推荐] 在不同系统时间下进入菜单页，推荐列表应反映当前时段的推荐菜品（如午餐时段 10:00-14:00 推荐午餐热门菜品，附带"午餐热门"标签）。
- [口味偏好] 推荐列表应包含与模拟用户口味画像 `tags` 匹配的菜品，并附带口味类推荐理由标签（如"辣味爱好者"）。
- [会话行为影响] 用户加购含特定 tag 的菜品后，后续推荐中同类 tag 菜品的推荐优先级应提升。
- [去重] 用户将推荐菜品加入购物车后，该菜品应从推荐列表中移除或标记"已加购"。
- [售罄过滤] 售罄菜品不应出现在推荐列表中。
- [加购衔接] 点击推荐菜品应弹出与现有点餐流程一致的规格选择 Dialog，加购行为与分类浏览加购完全一致。
- [搭配推荐] 购物车中已有主菜（broth/meat 类）时，推荐区域应出现"搭配推荐"模块，建议配菜/饮品组合。
- [一键组合加购] 点击"一键加入搭配"按钮后，搭配组合中的所有菜品应同时加入购物车（使用默认规格），购物车数量正确增加。
- [降级] 推荐数据不足时，推荐区域展示空态引导文案或隐藏推荐区域，不报错，不阻断点餐。
- [Tab 不变] 现有 `menu.cat.recommend` Tab 点击后仍显示全部菜品，行为与改动前一致。
- [兼容稳定] 推荐功能启用后，分类浏览、搜索、规格选择、超级辣提示、购物车、下单、订单、结账、呼叫服务等现有功能均正常，深色/老人模式/中英文切换均正常。
- [双语] 推荐相关文案（区域标题、推荐理由标签、搭配推荐、一键加购按钮、空态提示）在中英文下均正确显示。
