# 1. 背景与目标

## 1.1 背景

- 当前菜单页的"推荐"分类（`menu.cat.recommend`）实际为"显示全部菜品"的筛选入口，无任何智能推荐逻辑。
- 系统为纯前端 SPA（React 18 + TypeScript + Vite），无后端服务、无用户账号体系、无跨会话订单历史持久化，所有状态由 `useReducer` 在客户端管理。
- 菜品数据为静态演示数据（`src/data/menu.ts`，共 10 个菜品），部分菜品带有 `badge`（人气/招牌/主厨推荐/新品）和 `orderedCount`（已点台数）字段，但无结构化口味标签。
- 用户希望系统能根据历史点餐、菜品热度、口味标签、时段、搭配等多维度智能推荐，但当前架构不具备真实用户数据和推荐算法基础设施。

## 1.2 目标

| 目标 | 衡量方式 | 目标值 / 判断标准 |
|------|----------|-------------------|
| 提升用户点餐效率 | 用户进入菜单页即可看到推荐菜品，减少浏览决策时间 | 推荐区域展示 3-6 个推荐菜品 |
| 覆盖多维度推荐 | 推荐维度数量 | 至少覆盖 4 种推荐维度（热度、时段、口味偏好、搭配） |
| 推荐与点餐流程无缝衔接 | 推荐菜品可直接加购，流程与分类浏览一致 | 推荐菜品加购路径与现有流程完全一致 |
| 保持系统稳定性 | 推荐功能不影响现有功能 | 现有全流程（绑桌→点餐→下单→结账）正常，异常时静默降级 |

## 1.3 不做什么

- **不引入后端推荐服务或算法引擎**：推荐逻辑在前端客户端完成，不新增服务端接口（`/ping` 保持不变）。
- **不引入用户账号/登录体系**：推荐基于当前会话行为和模拟偏好画像，不依赖跨设备用户画像。
- **不修改现有点餐核心流程**：分类浏览、搜索、规格选择（份量/口味/辣度）、超级辣风险提示、购物车、下单、订单履约、结账等链路保持不变。
- **不重构菜单数据为动态接口**：菜品数据仍为 `src/data/menu.ts` 静态数据，推荐逻辑在此基础上计算。
- **不做 A/B 测试或推荐效果数据分析**：本次为概念演示功能，不接入数据采集和效果度量。
- **不做 localStorage 跨会话偏好持久化**：偏好画像为模拟数据，会话行为仅当前会话有效，不跨会话存储。
- **不引入机器学习库或外部推荐 SDK**：推荐逻辑为基于规则的客户端算法。

# 2. 用户与场景

| 用户 / 角色 | 使用场景 | 当前痛点 | 期望结果 |
|-------------|----------|----------|----------|
| 就餐用户（首次进入） | 绑桌后进入菜单页，面对 10 个菜品不知选什么 | 无推荐引导，选择困难 | 看到精选推荐菜品（基于模拟偏好+热度），快速决策 |

# 3. 功能需求

> 每条需求应独立、可验证，并尽量说明触发条件、系统行为和异常处理。

### REQ-001: 推荐区域展示

- **优先级**：P0
- **用户价值**：用户进入菜单页即可看到个性化推荐菜品，减少选择困难，提升点餐效率。
- **需求描述**：用户绑桌进入菜单页后，分类 Tab 上方展示"为你推荐"横滑卡片区域，包含 3-6 个推荐菜品，每张卡片附带推荐理由标签。
- **验收标准**：
  - [ ] REQ-001.1: The system shall 在菜单页分类 Tab 上方展示"为你推荐"横滑卡片区域，当用户进入菜单页时。
  - [ ] REQ-001.2: The system shall 展示 3-6 个推荐菜品，当可用推荐菜品数量充足时。
  - [ ] REQ-001.3: Each recommended dish card shall 附带 1-2 个推荐理由标签（如"人气 No.1""午餐热门""辣味爱好者"等）。
  - [ ] REQ-001.4: When 推荐菜品数量不足 3 个时, the system shall 展示所有可用推荐菜品并附空态引导文案。
  - [ ] REQ-001.5: If 推荐计算异常或无可用推荐菜品, then the system shall 隐藏推荐区域或展示"暂无推荐，请浏览全部菜品"，不报错，不阻断点餐。

```gherkin
Scenario: 用户进入菜单页看到推荐区域
  Given 用户已完成绑桌并进入菜单页
  When 页面加载完成
  Then 分类 Tab 上方应展示"为你推荐"横滑区域
  And 区域内包含 3-6 个推荐菜品
  And 每张卡片附带推荐理由标签
```

### REQ-002: 菜品热度排行推荐

- **优先级**：P0
- **用户价值**：让用户快速了解哪些菜受欢迎，辅助决策。
- **需求描述**：推荐逻辑基于菜品 `orderedCount` 和 `badge`（popular/signature/chef）排序，热度高的菜品优先推荐。
- **验收标准**：
  - [ ] REQ-002.1: The system shall 将 `orderedCount` 较高或 `badge` 为 popular/signature/chef 的菜品优先纳入推荐列表。
  - [ ] REQ-002.2: When 推荐列表包含热度菜品时, the system shall 附带热度类推荐理由标签（"人气 No.1" / "Top Pick"）。

### REQ-003: 时段推荐

- **优先级**：P1
- **用户价值**：推荐内容贴合当前就餐时段，提升推荐相关性。
- **需求描述**：根据当前系统时间划分时段，展示该时段热门菜品。时段划分：午餐 10:00-14:00、晚餐 17:00-22:00、夜宵 22:00-02:00（跨日），其他时段使用"全天热门"。
- **验收标准**：
  - [ ] REQ-003.1: When 当前时间处于 10:00-14:00 时, the system shall 推荐午餐热门菜品并附带"午餐热门"标签。
  - [ ] REQ-003.2: When 当前时间处于 17:00-22:00 时, the system shall 推荐晚餐热门菜品并附带"晚餐热门"标签。
  - [ ] REQ-003.3: When 当前时间处于 22:00-02:00（跨日）时, the system shall 推荐夜宵热门菜品并附带"夜宵热门"标签。
  - [ ] REQ-003.4: When 当前时间处于其他时段（02:00-10:00、14:00-17:00）时, the system shall 使用"全天热门"推荐，不标时段标签。
  - [ ] REQ-003.5: The system shall 定时检测当前时段是否变化，当时段切换时重新计算推荐。

```gherkin
Scenario: 午餐时段推荐
  Given 当前系统时间处于 10:00-14:00
  When 用户进入菜单页
  Then 推荐列表应包含午餐热门菜品
  And 推荐菜品附带"午餐热门"标签
```

### REQ-004: 口味偏好匹配推荐

- **优先级**：P0
- **用户价值**：推荐菜品匹配用户口味偏好，提升推荐个性化程度。
- **需求描述**：基于模拟用户口味画像（硬编码偏好 tags，如 `['辣','肉类','招牌']`），与菜品新增的 `tags` 字段做匹配，匹配度高的菜品优先推荐。会话内用户加购行为动态调整推荐权重。
- **验收标准**：
  - [ ] REQ-004.1: The system shall 使用模拟用户口味画像（硬编码 tags）与菜品 `tags` 字段匹配，匹配度高的菜品优先推荐。
  - [ ] REQ-004.2: When 用户在会话中加购含特定 tag（如 `['辣']`）的菜品时, the system shall 提升该 tag 类菜品在后续推荐中的权重。
  - [ ] REQ-004.3: When 推荐列表包含口味匹配菜品时, the system shall 附带口味类推荐理由标签（如"辣味爱好者"）。
  - [ ] REQ-004.4: The system shall 在 `RESET` 后恢复模拟偏好画像初始值。

### REQ-005: 搭配推荐

- **优先级**：P1
- **用户价值**：当用户已选主菜时，建议搭配配菜和饮品，提升搭配体验和客单价。
- **需求描述**：购物车内已有主菜（category 为 `menu.cat.broth` 或 `menu.cat.meat`）时，推荐互补菜品（category 为 `menu.cat.veggie` 或 `menu.cat.staple`），组成"主菜+配菜+饮品"搭配，展示"一键加入搭配"按钮。
- **验收标准**：
  - [ ] REQ-005.1: When 购物车中已有主菜（broth/meat 类）时, the system shall 在推荐区域出现"搭配推荐"模块，建议配菜/饮品组合。
  - [ ] REQ-005.2: The system shall 展示 2-3 个搭配菜品组合建议。
  - [ ] REQ-005.3: When 用户点击"一键加入搭配"时, the system shall 将搭配组合中的所有菜品同时加入购物车（使用默认规格）。
  - [ ] REQ-005.4: The system shall 允许用户逐个点击搭配卡片中的菜品单独加购（弹出规格选择 Dialog）。
  - [ ] REQ-005.5: The system shall 随购物车内容变化动态更新搭配推荐。

```gherkin
Scenario: 搭配推荐一键加购
  Given 购物车中已有主菜（如牛肉）
  When 推荐区域出现搭配推荐模块
  And 用户点击"一键加入搭配"
  Then 搭配组合中的所有菜品应同时加入购物车
  And 购物车数量正确增加
```

### REQ-006: 推荐去重与售罄过滤

- **优先级**：P0
- **用户价值**：避免重复推荐已选/售罄菜品，提升推荐质量。
- **需求描述**：已加入购物车的菜品在推荐列表中标记"已加购"并降低优先级或移出推荐列表。售罄菜品不出现在推荐列表中。
- **验收标准**：
  - [ ] REQ-006.1: When 菜品已加入购物车时, the system shall 在推荐列表中标记"已加购"或将其移出推荐列表。
  - [ ] REQ-006.2: The system shall 不将 `soldOut` 列表中的菜品纳入推荐列表。
  - [ ] REQ-006.3: When 购物车发生变化（加购/改数量/移除）时, the system shall 重新计算推荐列表。

### REQ-007: 推荐刷新时机

- **优先级**：P1
- **用户价值**：推荐列表实时反映用户行为和时段变化，保持推荐新鲜度。
- **需求描述**：推荐在用户进入菜单页时初次计算，购物车变化时重新计算，时段切换时重新计算。
- **验收标准**：
  - [ ] REQ-007.1: The system shall 在用户进入菜单页时初次计算推荐。
  - [ ] REQ-007.2: When 购物车发生变化（加购/改数量/移除）时, the system shall 重新计算推荐。
  - [ ] REQ-007.3: When 当前时段发生变化时, the system shall 重新计算推荐。

### REQ-008: 推荐菜品加购衔接

- **优先级**：P0
- **用户价值**：推荐菜品可直接加购，与现有流程一致，无额外学习成本。
- **需求描述**：点击推荐菜品卡片弹出与现有点餐流程一致的规格选择 Dialog，加购行为与分类浏览加购完全一致。
- **验收标准**：
  - [ ] REQ-008.1: When 用户点击推荐菜品卡片时, the system shall 弹出规格选择 Dialog（份量/口味/辣度/用餐人）。
  - [ ] REQ-008.2: The system shall 确保推荐菜品加购行为与分类浏览加购完全一致（含超级辣风险提示）。

### REQ-009: 降级与异常处理

- **优先级**：P0
- **用户价值**：推荐功能异常时不影响核心点餐流程。
- **需求描述**：推荐逻辑异常或数据不足时，降级为隐藏推荐区域或回退为展示全部菜品，不阻断点餐流程。
- **验收标准**：
  - [ ] REQ-009.1: If 推荐计算出错, then the system shall 静默降级（隐藏推荐区域），用户无感知，不影响正常点餐。
  - [ ] REQ-009.2: If 无可用推荐菜品（如全部售罄）, then the system shall 展示空态引导文案"暂无推荐，请浏览全部菜品"。

### REQ-010: 中英文双语支持

- **优先级**：P1
- **用户价值**：推荐功能与现有国际化体系一致。
- **需求描述**：推荐相关文案（区域标题、推荐理由标签、搭配推荐、一键加购按钮、空态提示、已加购标记）在中英文下均正确显示。
- **验收标准**：
  - [ ] REQ-010.1: The system shall 在中英文切换后正确显示所有推荐相关文案。

# 4. 产品规则

## 4.1 页面与交互

| 位置 / 入口 | 用户操作 | 系统反馈 | 备注 |
|-------------|----------|----------|------|
| 菜单页分类 Tab 上方 | 用户进入菜单页 | 展示"为你推荐"横滑卡片区域，3-6 个推荐菜品 | 推荐区域独立于 Tab 系统，不遮挡搜索框和分类 Tab |
| 推荐菜品卡片 | 用户点击推荐菜品 | 弹出规格选择 Dialog（与现有流程一致） | 加购行为与分类浏览完全一致 |
| 推荐区域"已加购"标记 | 菜品已加入购物车 | 推荐卡片标记"已加购"或移出推荐列表 | 推荐列表动态补充新菜品 |
| 搭配推荐模块 | 购物车已有主菜 | 出现"搭配推荐"模块，展示 2-3 个搭配组合 | 附带"一键加入搭配"按钮 |
| "一键加入搭配"按钮 | 用户点击 | 搭配组合所有菜品同时加入购物车（默认规格） | 用户也可逐个点击搭配卡片单独加购 |
| 推荐横滑区域 | 用户横滑/拖拽 | 卡片横向滚动，滚动条隐藏 | 支持触摸滑动和鼠标拖拽 |

### UX 设计原则

- 推荐区域为横滑卡片布局，卡片宽度小于分类浏览网格卡片（紧凑展示）。
- 与现有菜单卡片视觉风格一致（圆角卡片 + 图片 + 名称 + 价格 + 推荐理由标签）。
- 推荐理由标签使用现有 badge 视觉样式（圆角胶囊 + 琥珀色底），不引入新色系。
- 推荐区域在浅色/深色模式、老人模式下均正常显示，卡片间距、字号、对比度满足现有设计规范。
- 推荐区域不遮挡或推开分类 Tab 和搜索框。
- 横滑区域支持触摸滑动和鼠标拖拽，滚动条隐藏（`scrollbar-none`）。

## 4.2 字段与校验

# 6. UX Design

## 体验目标与设计原则

- 推荐菜是点餐流程的辅助，不应打断点餐路径。
- 推荐区域与现有菜单分类区域视觉区分，用户能直观识别"推荐"与"全部菜品"。
- 推荐理由标签简洁明了，帮助用户快速理解推荐原因。

## 页面 / 模块 / 入口范围

- 入口：菜单页（`MenuView` 组件），分类 Tab 上方新增推荐区域。
- 模块：推荐横滑卡片区域 + 搭配推荐模块（条件展示）。

## 核心体验路径

1. 用户绑桌进入菜单页 → 分类 Tab 上方显示"为你推荐"横滑卡片区域。
2. 用户横滑浏览推荐菜品，看到推荐理由标签。
3. 用户点击推荐菜品 → 弹出规格选择 Dialog → 加购。
4. 推荐区域自动刷新，已加购菜品标记或移出。

## 分支路径 / 异常路径

- **空态**：无可用推荐菜品时，展示引导文案"暂无推荐，请浏览全部菜品"。
- **降级**：推荐计算异常时，静默隐藏推荐区域，不报错。
- **搭配空态**：购物车无主菜时，不展示搭配推荐模块。

## 文案与可理解性

| 文案位置 | 中文 | 英文 |
|----------|------|------|
| 推荐区域标题 | 为你推荐 | Recommended For You |
| 热度类标签 | 人气 No.1 | Top Pick |
| 时段标签-午餐 | 午餐热门 | Lunch Favorite |
| 时段标签-晚餐 | 晚餐热门 | Dinner Favorite |
| 时段标签-夜宵 | 夜宵热门 | Late Night Favorite |
| 口味类标签 | 辣味爱好者 | Spicy Lover |
| 搭配类标签 | 搭配牛肉 | Pairs with Beef |
| 已加购标记 | 已加购 | Added |
| 空态提示 | 暂无推荐，请浏览全部菜品 | No recommendations, browse all dishes |
| 搭配推荐标题 | 搭配推荐 | Combo Suggestions |
| 一键加购按钮 | 一键加入搭配 | Add Combo |

## 视觉与响应式约束

- 推荐卡片为紧凑横滑卡片，宽度小于分类网格卡片。
- 推荐理由标签使用现有 badge 视觉样式（圆角胶囊 + 琥珀色底）。
- 横滑区域滚动条隐藏（`scrollbar-none`）。
- 浅色/深色模式、老人模式下视觉一致性。

# 7. Backend/Data

## 数据模型变更

| 对象 / 类型 | 变更 | 说明 | 兼容性 |
|-------------|------|------|--------|
| `Product` 接口（`src/types.ts`） | 新增 `tags?: string[]` 可选字段 | 存储菜品口味标签，用于推荐匹配 | 向后兼容（可选字段） |
| `AppState`（`src/types.ts`） | 可新增推荐相关 state 字段 | 存储推荐列表、模拟画像、会话行为权重 | 向后兼容（新增字段） |
| `src/data/menu.ts` 菜品数据 | 为现有 10 个菜品补充 `tags` 字段 | 提供推荐匹配所需口味标签数据 | 向后兼容 |

## 推荐逻辑行为规则

- 推荐逻辑为客户端基于规则的算法（非 ML），在前端同步完成。
- 推荐计算输入：菜品数据（含 tags）、模拟用户画像、购物车内容（会话行为）、当前时间（时段）、售罄列表。
- 推荐计算输出：推荐菜品列表（排序后 3-6 个）+ 每个菜品的推荐理由标签。
- `RESET` 后恢复初始模拟画像和推荐状态。

## 存储变更

- 无数据库变更（纯前端，无后端存储）。
- 无 localStorage 变更（模拟画像不跨会话持久化）。
